FINDING mid-verification: the FIRST pass through this scenario rendered
scene 3's slot as "image", not "failed" — a real, pre-existing bug in T1's
`deriveState` (canvas-shared/timeline-slots.ts), which checked
`asset.image_url` BEFORE the video_status/animation_status failure markers.
T1's own comment called this "clip/image truth wins precedence" on the
theory a failure marker might be stale — but a clip is always animated FROM
an existing image, so `image_url` being set was never real evidence a CLIP
attempt succeeded; it only proved the earlier IMAGE stage worked. Since this
exact case (image done, clip failed) is the primary scenario T5b exists to
surface, shipping T5b's backend write without this fix would have persisted
a marker the timeline could still never show for its main use case. Fixed
by moving the video_status/animation_status check ahead of the image_url
check in deriveState (backend now also guarantees the marker can't go stale:
the clip-success write clears video_status=NULL in the same statement as
video_clip_url, same as the existing picture-redraw path already did).
Existing test "a clip already present beats a stale failure marker" was
updated to match — see timeline-slots.test.ts (14/14 passing, stash-proofed
both directions).
