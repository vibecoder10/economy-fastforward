## chat-director - Chat as an intelligent director (intake -> generation)  `[wired]`

**Actual:** The chat is genuinely wired end-to-end and is NOT orphaned: a real user's POST /api/chat hits one mounted router and drives the real pipeline. The intake producer (producer_prompt.call_producer, a real direct-Anthropic call) runs every turn; approving a plan creates a real video and auto-builds research -> script -> pictures via PipelineExecutor + generate_coverage_for_video (real GPT Image 2 generation); the in-video co-pilot classifies plain-English requests and runs real executor methods (run_clip_generation, run_render, run_images, run_thumbnail, etc.) behind a paid-confirm gate. BUT the "intelligent director" intelligence is shallow and front-loaded: (1) The proactive idea recommendation only fires ONCE, inside first-time onboarding (modeling -> ideas steps). A returning, already-onboarded user who opens the home chat gets a STATIC generic greeting (the dragon example) plus raw "worth modeling" cards - never a proactively pitched "here's the video I'd make for you today." (2) On every normal intake turn the producer is given only intent/goals/channel-name/competitor-names/niche (the _creator_brief) plus a runtime length anchor. It is NEVER given the competitors' actual winning titles, hooks, thumbnails, or proven format patterns - despite the producer_prompt docstring claiming it injects "proven titles/hooks/look." So the producer's script/style/hook/thumbnail suggestions are generic, not modeled on what wins for this channel except for length. (3) The module's own self-test is broken (asserts a substring that does not exist), so this code's "proof" passes vacuously - the exact pattern of fixes that look done but aren't.

**Root-cause gaps:**

- **[MAJOR]** The proactive 'recommend a video idea from channel + competitors' only exists inside the one-time onboarding flow. A returning, already-onboarded user who opens the home chat is NOT pitched an idea on start. The chat_turn dispatcher (chat.py:1995) only enters the idea-pitching path when state.mode == 'onboarding'; otherwise a user with no message gets the static generic _GREETING. _generate_competitor_ideas / _present_ideas_turn are reachable ONLY from the onboarding 'modeling' step (chat.py:1921). The spec's 'on start it recommends a video idea' therefore fires once, ever, not on each return.
  - _evidence:_ chat.py:1995 `if not video_id and (body.start_onboarding or state.get("mode") == "onboarding"):` is the ONLY gate into onboarding; chat.py:2022-2029 the no-message branch returns the static `_GREETING` (chat.py:45 'Tell me about the video you want to make...the dragon...') with no idea pitch; chat.py:1921 `ideas = await _generate_competitor_ideas(...)` sits inside `_handle_onboarding` step=='modeling' only.
  - _files:_ storyengine/backend/routes/chat.py
- **[MAJOR]** The producer's every-turn channel intelligence is hollow: it receives only intent/goals/channel-name/competitor-names/niche plus a length anchor. It is never given the competitors' real winning titles, hooks, thumbnails, or format patterns - so its script/style/hook/thumbnail recommendations are generic, contradicting the spec ('model script, style, hooks, thumbnail, cadence') and the module's own docstring. The competitor format data IS fetched elsewhere (_recent_competitor_rows / _video_lines) but is wired only into the one-shot onboarding idea generator, never into build_system_prompt for ongoing turns.
  - _evidence:_ chat.py:2046 `system_prompt = build_system_prompt(_creator_brief(state) + await _modeled_runtime_hint(tenant_id))` - the only two brief sources; _creator_brief (chat.py:1374-1403) emits only intent/goals/channel/competitor-names/niche; saved brief keys _BRIEF_KEYS = ('intent','goals','niche_angle','channel','competitors') (chat.py:1427) carry NO titles/hooks/thumbnails; grep for competitor_videos/hooks feeding build_system_prompt returns nothing. producer_prompt.py:107 docstring claims it injects 'proven titles/hooks/look' - the data never arrives.
  - _files:_ storyengine/backend/routes/chat.py, storyengine/backend/producer_prompt.py
- **[MINOR]** The producer module's self-test - the supposed proof this behaves - is broken and asserts against a string that does not exist, so `python3 producer_prompt.py` raises AssertionError before any live check. This is the owner's exact pain: a 'proof harness' that gives false confidence. The header was renamed to '--- THIS CREATOR'S CHANNEL ---' but the assertion still checks for 'MY CHANNEL'.
  - _evidence:_ producer_prompt.py:230 `assert "MY CHANNEL".lower() in build_system_prompt("Niche: cooking").lower()` but producer_prompt.py:112 renders header `--- THIS CREATOR'S CHANNEL ---`; verified at runtime: 'my channel' in 'this creator\'s channel' == False, so the offline self-check fails.
  - _files:_ storyengine/backend/producer_prompt.py
- **[MINOR]** The co-pilot's proactivity is reactive-only: it acts when the user asks ('animate scene 2'), but nothing proactively volunteers the next best director move (e.g. 'these pictures are weak, want me to redo scene 3?' or 'your competitor's hook is stronger - rewrite the opening?'). The spec's 'proactively suggests' is only half-met: the system runs actions on request well, but does not volunteer director-grade next steps; its empty-message default just lists options.
  - _evidence:_ producer_prompt.py:51 'NEVER mention internal machinery...pipeline, stage, status, render, storyboard'; _handle_copilot (chat.py:854-887) classifies only what the user said into read|action|prompt and returns - there is no branch that inspects _copilot_summary state to volunteer an unsolicited improvement; the co-pilot's empty-message default (chat.py:813-815) lists options rather than recommending one.
  - _files:_ storyengine/backend/routes/chat.py, storyengine/backend/producer_prompt.py

**Root fix:** Make channel/competitor intelligence a first-class, always-on input to the producer rather than a one-time onboarding seed. Root changes: (1) Build a durable, richer creator brief: persist the modeled channel's proven format - top titles, hook patterns, thumbnail motifs, median cadence/runtime - onto channel_profiles (not just the 5 thin _BRIEF_KEYS), refreshed when competitor scrapes complete. (2) Feed that rich brief into build_system_prompt on EVERY producer turn (chat.py:2046 and _seed_producer) so suggestions are genuinely modeled, fulfilling the docstring's promise. (3) Add a proactive 'open turn' for returning users: when chat_turn gets no message and the user is already onboarded with competitor data, run the existing _generate_competitor_ideas/_present_ideas_turn path to pitch a fresh modeled idea on start, instead of the static _GREETING. (4) Give the co-pilot a proactive director pass: after any read/action, let it inspect the video summary and optionally volunteer one concrete next-best move as a tappable suggestion. (5) Fix the producer_prompt self-test assertion (and add a real test that asserts competitor format data actually reaches the system prompt) so the proof harness can't pass vacuously again.

## style-detect-apply - Style: detect the modeled video style, ask/recommend, apply end-to-end  `[partial]`

**Actual:** There are TWO disconnected halves that do not meet on the main (chat-first) user path.

DETECTION (real and good, but only on two minority entry points): routes/model_video.py runs a genuine style classifier. _describe_scene_style() (model_video.py:380) does a vision pass over real mid-video frames (i.ytimg.com hq1/2/3.jpg) and forces a `MEDIUM:` line naming photorealistic/3D-Pixar/2D/anime, with an explicit "do NOT default to animated/illustrated" instruction. The resulting image_dna is written to videos.image_style_override by _persist_pack (model_video.py:550) and _persist_style_overrides (model_video.py:674). This runs ONLY when (a) the user pastes a URL into the standalone "Model A Video" modal -> POST /api/model-video, or (b) the user pastes a URL into the Create-form "copy a video" field -> create_video sets is_modeled=True and calls _run_modeling (videos.py:265-274).

APPLICATION (real and good, just shipped in e19f5241): coverage_to_app.py:_resolve_style reads videos.image_style_override/visual_style and threads it through build_cast_prompt, _storyboard_sheet_system, populate_characters, and run_coverage. coverage.py locks every frame to the cast sheet's style (_STYLE_LOCK, coverage.py:193), and clips are image-to-video so they inherit the frame's style. This IS wired live: routes/pipeline.py exposes /storyboard-images (->generate_storyboard_sheet_for_scene) and /coverage-images (->generate_coverage_for_video), and routes/chat.py auto-build calls generate_coverage_for_video directly (chat.py:304).

THE BREAK: the primary chat-first path never connects them. The "Worth modeling" home card click sends a plain TEXT message ("Make a video modeled on \"<title>\"...") with no URL/video-id/detected style (ChatCore.tsx:431). The chat producer (producer_prompt.py) is never told the modeled video's style — it only gets a creator brief + a LENGTH anchor (_modeled_runtime_hint, chat.py:1406, length only). The producer then offers a generic 6-option style card or guesses, and _spec_to_create_request never sets reference_url (chat.py:393), so the chat-created video is never is_modeled, _run_modeling never fires, and no style is detected. If the producer/creator don't set a style, image_style_override is NULL, _resolve_style returns style_dir=None, and build_cast_prompt falls back to "a PHOTOREAL live-action / 3D-CG style" (coverage_to_app.py:95) — i.e. realistic, the exact failure the owner described.

**Root-cause gaps:**

- **[BLOCKER]** The chat-first 'Worth modeling' / 'model this video' flow — the product's primary modeling entry per the owner's own memory notes — never passes the reference video to the detector. The home card click degrades the modeled video to a plain title string in a chat message, so the producer has zero knowledge of the source video's actual visual style and cannot recommend or pre-select it. Detection (model_video.py's scene-frame vision classifier) is bypassed entirely. This is exactly the owner's 'orphaned code mistaken for a working feature' trap: the detector is real and good but unreachable from the path users actually take to model a video in chat.
  - _evidence:_ ChatCore.tsx:431 onPick sends only `Make a video modeled on "${v.title}" from ${channel} — same hook and winning format, but my own spin.` (no URL, no video_id, no style). chat.py:2046 `system_prompt = build_system_prompt(_creator_brief(state) + await _modeled_runtime_hint(tenant_id))` — the only modeled-video signal injected is LENGTH (chat.py:1421-1423). producer_prompt.py:95 the LOOK card is a fixed generic 6-option list with 'Don't invent other style values'; nothing carries the detected source style in.
  - _files:_ storyengine/frontend/src/components/chat/ChatCore.tsx, storyengine/backend/routes/chat.py, storyengine/backend/producer_prompt.py
- **[MAJOR]** Chat-created videos can never reach the detection path because _spec_to_create_request omits reference_url, so create_video's is_modeled is always False and _run_modeling never fires from chat. Detection is structurally fenced off from the chat producer regardless of what the user clicked.
  - _evidence:_ chat.py:393-404 _spec_to_create_request returns CreateVideoRequest(... no reference_url ...). videos.py:215-225 `reference_url = (body.reference_url or '').strip() or None ... is_modeled = reference_youtube_id is not None` and videos.py:265 `if is_modeled:` gates the only call to _run_modeling. This is the precise 'renders realistic instead of Pixar' symptom; the e19f5241 fix only made application honor a style that was *already picked*, it did not remove the realistic fallback for the no-style case.
  - _evidence:_ coverage_to_app.py:95 `style_line = style.strip() if (style and style.strip()) else "a PHOTOREAL live-action / 3D-CG style"`; coverage_to_app.py:234 populate_characters else-branch `" Photoreal and realistic, ... never 2D illustration or cartoon."`; coverage_to_app.py:420 _storyboard_sheet_system else `"Photorealistic, cinematic film still"`. _resolve_style returns style_dir=None when both DB fields are empty (coverage_to_app.py:89), so all three default to realistic.

Concretely: (1) Make the 'Worth modeling' click carry the source video's identity, not a title string — onPick should pass v.video_id/reference URL through the chat turn (a structured field on the chat request, e.g. modeled_reference_url), not bury it in free text. (2) On that turn, run (or reuse a cached) style detection for the reference (model_video.py's _describe_scene_style/image_dna) and inject the detected MEDIUM into the producer system prompt as a recommended style, and pre-select the matching VISUAL_PRESETS id on the LOOK card so the creator confirms '3D Pixar' rather than guessing. (3) Persist that detected/confirmed style as image_style_override on the chat-created video so the already-correct application chain renders it. (4) Replace the silent realistic fallback in coverage_to_app.py (lines 95/234/420) with a hard requirement: if a video was modeled from a reference but has no resolved style, block and surface 'set the style' (the blockers mechanism already exists in model_video.py) rather than defaulting to photoreal. This makes detection->ask/recommend->apply one continuous path on the flow users actually use, and removes the realistic default that produces the owner's exact complaint.

## length-director - Length recommendation from the modeled video + natural warnings  `[wired]`

**Actual:** The chat producer DOES recommend a length, render a slider pre-set to that recommendation, send the chosen seconds to the backend, and that length really does drive act count, scene count, and word targets in both live script paths (legacy brief-translator and modeled-script). So the core loop is wired and working. BUT the "recommended length from THE example video" is not what actually happens in chat: the only length anchor the producer receives is a tenant-wide MEDIAN of all competitor_videos durations (_modeled_runtime_hint), never the specific video the user chose to model. The specific reference video's exact runtime IS used correctly — but only in the separate, non-chat model_video.py flow, which silently sets the length and never asks the user or warns at all. The "too short" warning is purely LLM-generated free text in the producer's assistant_text (no deterministic guard); the only deterministic warning is a frontend band-hint under the slider (lengthHint), which is generic and not tied to the modeled video. Net: two divergent length flows, and the headline intent ("recommend based on the example video, in chat, with a warning") is only partially met.

**Root-cause gaps:**

- **[MAJOR]** The chat producer's length recommendation is NOT based on the specific video the user is modeling. _modeled_runtime_hint computes the MEDIAN duration across ALL of the tenant's competitor_videos, not the runtime of the one video being modeled. So a user who says 'model this 12-minute video' gets a recommendation anchored to their channel-wide median (could be 6 min), directly contradicting the intent 'recommended length based on the example video'. The specific video's runtime is never passed into the producer transcript or brief (seed_text at chat.py:1673 carries the idea text, not the runtime).
  - _evidence:_ chat.py:1411-1413: `SELECT percentile_cont(0.5) WITHIN GROUP (ORDER BY duration_seconds) AS med FROM competitor_videos WHERE tenant_id = $1 AND duration_seconds > 0` — a tenant-wide median, not the modeled video's row. chat.py:1421: `LENGTH ANCHOR: the videos this creator models typically run ~{med}` (plural 'videos', generic). The producer prompt promises the opposite at producer_prompt.py:96: `If they're modeling a specific video and you know its runtime, anchor to it: "the video you're modeling runs ~8 min"` — but the specific runtime is never supplied.
  - _files:_ storyengine/backend/routes/chat.py
- **[MAJOR]** Two divergent length flows that don't share logic. The direct 'model this video' path (model_video.py) sets the length to the specific reference's exact runtime and NEVER asks the user or warns — and it clamps to a 3-minute minimum, so a genuinely short reference is silently inflated. The chat producer path asks + warns but uses the wrong (median) anchor. The intended single behavior (recommend the example's length, let user set, warn if too short) exists in neither flow completely.
  - _evidence:_ model_video.py:474-475: `duration = info.get("duration_seconds") or 0` then `video_length_minutes = min(30, max(3, round(duration / 60))) if duration else 10` — exact reference runtime, no user prompt, no warning, hard floor of 3 min. This path writes the videos row directly; the chat producer/_modeled_runtime_hint logic is bypassed entirely.
  - _files:_ storyengine/backend/routes/model_video.py, storyengine/backend/routes/chat.py
- **[MINOR]** The 'too short' warning has no deterministic backstop on the chat path. The story-specific warning ('under a minute is tight for a real arc') is only LLM-generated assistant_text governed by the producer prompt; if the model omits it (or the producer call fails soft to _FALLBACK), the only warning the user sees is the generic frontend band-hint, which is hardcoded by second-range and unaware of the story or the modeled video.
  - _evidence:_ producer_prompt.py:96 puts the entire short-video warning inside prose instructions to the LLM (no code enforces it). producer_prompt.py:198-199 + _FALLBACK (146-149) return a length-free gentle reprompt on failure. The only deterministic warning is ChatCore.tsx:94-100 lengthHint(secs), a fixed band lookup: `if (secs < 90) return "Tight for a real story..."` — generic, not tied to the modeled video or the actual story.
  - _files:_ storyengine/backend/producer_prompt.py, storyengine/frontend/src/components/chat/ChatCore.tsx
- **[MINOR]** Minor schema inconsistency in the producer contract: the cards JSON schema enumerates card type as only 'single' | 'multi' (producer_prompt.py:69) while the LENGTH guidance instructs the model to emit "type":"slider" (producer_prompt.py:96). Detection survives because both backend and frontend also match on id == 'length', so the slider still renders — but the contradictory contract invites the model to emit a malformed/mismatched card.
  - _evidence:_ producer_prompt.py:69 schema: `"type": "single" | "multi"`; producer_prompt.py:96 guidance: `ALWAYS offer the length card ("id":"length", "type":"slider"...)`. Saved by id-based detection at chat.py:149 (`c.get("id") == "length" or c.get("type") == "slider"`) and ChatCore.tsx:75.
  - _files:_ storyengine/backend/producer_prompt.py

**Root fix:** Unify the two length flows around a single source of truth: the specific modeled video's runtime. (1) When a chat conversation is seeded from a modeled idea, pass that specific video's duration_seconds into the producer brief instead of (or in addition to) the tenant median — e.g. replace/augment _modeled_runtime_hint with a per-video runtime hint that reads the duration of the exact video being modeled (the modeled_pack / competitor_videos row tied to this idea), so the producer's 'anchor to it' instruction (producer_prompt.py:96) actually has the real number. Keep the median only as a fallback when no specific video is in play. (2) Make model_video.py route through the same recommend-and-confirm step rather than silently writing a 3-min-floored length, so the 'let the user set it + warn' behavior is consistent no matter how the user enters. (3) Add a deterministic short-length guard server-side (not just LLM prose): if chosen seconds fall below a story-beats threshold, attach a structured warning to the turn so it surfaces even when the LLM omits it or the producer call fails soft. (4) Fix the card-type schema contradiction in producer_prompt.py so 'slider' is a declared type. This removes the median-vs-specific mismatch (the actual root cause), collapses the divergent flows, and makes the warning robust instead of model-dependent.

## grok-imagine prompting research (kie.ai)

1. **Build the I2V prompt as a motion script, not a description. Use the formula: [Subject + its motion] + [Camera + its move] + [Lighting/atmosphere shift]. Example that works: 'Man raises his coffee cup slowly, dolly zoom pushing toward his face, morning light intensifying to warm gold as steam rises.' Do NOT re-describe what is already in the image; the model sees it.** _Why:_ Grok's image-to-video model treats the input frame as fixed scene context. Re-describing the scene wastes the prompt; describing change (action + camera + light) is what actually animates. Both kie.ai-aligned guides converge on this Subject+Motion / Camera+Motion / Background+Motion structure. [https://www.atlascloud.ai/blog/guides/grok-image-to-video]
2. **Put the most important motion and camera instruction FIRST in the prompt. The Aurora engine reads left-to-right and tail-end actions can get dropped. Front-load the camera move and the key subject action; push lighting/atmosphere to the end.** _Why:_ The model processes prompts sequentially and truncates effort toward the tail, so late instructions risk never rendering. Ordering is a real lever on output, not cosmetic. [https://www.atlascloud.ai/blog/guides/grok-image-to-video]
3. **Never contradict the input image. If the subject is seated, do not prompt running; actions must be physically reachable from the frame's existing pose, framing, and environment, or you get incoherent output.** _Why:_ The input frame is immutable for I2V. Prompting motion that conflicts with the starting pose produces broken or warped results. This is the single most common cause of bad I2V clips. [https://www.grokimagineai.net/prompt-guide]
4. **Do NOT use negative prompts. Grok Imagine's video model ignores them. Express what you want positively instead of listing what to avoid.** _Why:_ Confirmed in multiple Grok prompt guides: negative prompts have no effect on this model, so any 'no X, avoid Y' tokens are wasted prompt budget. [https://www.grokimagineai.net/prompt-guide]
5. **Specify camera moves with concrete cinematic verbs placed early: dolly forward/push-in, pull-back, pan left/right, tilt up/down, tracking/follow shot, crane, aerial, orbit/arc around subject, dolly zoom, slow zoom, handheld sway. Use one clear move per clip for control. Add 'Unfixed lens' when including camera movement and 'Fixed lens' for a locked static shot.** _Why:_ Grok 1.5 executes named camera moves cleanly without the stutter of older models, but only when you name the move explicitly. The Fixed/Unfixed-lens toggle is the model's documented way to lock or free the camera. [https://www.grokimagineai.net/prompt-guide]
6. **Control motion intensity with adverbs of degree: 'quickly', 'slowly', 'violently', 'with large amplitude', 'at high frequency', 'powerfully', 'wildly'. Example: change 'car passing' to 'car passing quickly'. Give the model a concrete beat ('she takes one step back, turns her head 30 degrees left, the coat hem catches the wind') instead of mood words ('cinematic and dramatic') which give it nothing to animate.** _Why:_ Vague mood adjectives produce near-static or random motion. Quantified, beat-level motion verbs are what produce real, directed movement. This is the difference between a live shot and a slightly-moving photo. [https://www.grokimagineai.net/prompt-guide]
7. **Sequence multiple actions in order within one prompt using: 'subject + movement 1 + movement 2' or 'subject 1 + movement 1 + subject 2 + movement 2'. Use 'Shot Switch' to cut between distinct shots with a clear transition inside a single clip.** _Why:_ The model sequences listed actions in the order given, so ordering controls timing. 'Shot Switch' is the documented keyword for an intentional cut within one generation. [https://www.grokimagineai.net/prompt-guide]
8. **For shot type / framing, state it plainly at the front: 'wide shot', 'medium shot', 'close-up', 'extreme close-up', 'low-angle', 'high-angle', 'POV', 'over-the-shoulder', 'aerial'. For I2V the framing is mostly set by the input image, so use the shot word to guide the camera move (e.g. push from a wide into a close-up) rather than to re-frame from scratch.** _Why:_ I2V inherits framing from the still, so shot-type language is most effective as a target for the camera move. Treating it like text-to-video reframing tends to fight the input image. [https://www.atlascloud.ai/blog/guides/grok-image-to-video]
9. **Keep one character consistent across multiple clips by feeding the SAME source/reference image of that character into every clip, keeping the character portrait isolated to its own image slot, and reusing the same descriptive name/tag for them in each prompt. Avoid overlapping or conflicting backgrounds across reference slots.** _Why:_ Grok 1.5 improves visual consistency but has no persistent character memory across separate API calls. The reliable lever is anchoring every clip to the identical reference image plus a stable verbal tag; nothing else carries identity between clips. [https://kie.ai/grok-imagine]
10. **Reference an uploaded image inside the prompt with the literal syntax '@image1 ' (the token '@image' + the image's 1-based position, followed by a space), e.g. '@image1 a sunset over the ocean'. For image-to-image / multi-image generation you can chain tags in submission order ('@image1 walks carrying @image3 while @image2 watches'). IMPORTANT: for grok-imagine IMAGE-TO-VIDEO only ONE image is used as the motion reference - extra images are ignored ('only the first will be used'), so the @image tag mainly matters for the multi-image and image-to-image endpoints.** _Why:_ The @image tag is how you tell the model which uploaded asset is which subject. But the video endpoint is single-reference, so a multi-@image character/prop/environment composition must be assembled at the image stage (image-to-image), then animated, not done in one I2V call. Mis-assuming multi-image I2V is a real failure mode. [https://docs.kie.ai/market/grok-imagine/image-to-image]
11. **Vary shot duration per clip via the 'duration' parameter, range 6-30 seconds in 1-second increments. Note the default differs by mode: image-to-video example uses duration as a STRING (e.g. "6"); text-to-video uses it as a NUMBER (e.g. 6). For short-form cutting, request short native clips (6s) and stitch rather than generating one long take.** _Why:_ Duration is the explicit length control and it is per-request, so different shots in a sequence can have different lengths. The string-vs-number type difference between the I2V and T2V payloads is a concrete gotcha that will cause request errors if mismatched to the wrong endpoint. [https://docs.kie.ai/market/grok-imagine/image-to-video]
12. **Resolution is '480p' or '720p' (default 480p); aspect_ratio is one of '2:3','3:2','1:1','16:9','9:16' (I2V default 16:9, T2V default 2:3); for I2V, if aspect_ratio is omitted it follows the input image's size. Prompt is English-only, max 5000 characters for video.** _Why:_ These are the exact allowed values; passing anything else fails validation. The 'follows image size' behavior for I2V matters because forcing a mismatched aspect ratio against the source image can crop or distort the subject. [https://docs.kie.ai/market/grok-imagine/text-to-video]

**kie.ai specifics:**
- Base URL: https://api.kie.ai . All jobs go to POST /api/v1/jobs/createTask (full: https://api.kie.ai/api/v1/jobs/createTask).
- Auth headers on every request: 'Authorization: Bearer <YOUR_API_KEY>' and 'Content-Type: application/json'. Create/get keys at https://kie.ai/api-key . Missing/bad key returns {"code":401,"msg":"You do not have access permissions"}.
- Model id for image-to-video: 'grok-imagine/image-to-video'. For text-to-video: 'grok-imagine/text-to-video'. For image-to-image (multi-@image composition stage): 'grok-imagine/image-to-image'. Model id is passed as the top-level 'model' field; all generation params go inside an 'input' object.
- Image-to-video payload shape: {"model":"grok-imagine/image-to-video","callBackUrl":"https://your-domain.com/api/callback","input":{"image_urls":["https://...png"],"prompt":"<motion script>","mode":"normal","duration":"6","resolution":"480p","aspect_ratio":"16:9"}}. Note duration is a STRING here.
- Text-to-video payload shape: {"model":"grok-imagine/text-to-video","callBackUrl":"...","input":{"prompt":"...","aspect_ratio":"2:3","mode":"normal","duration":6,"resolution":"480p"}}. Note duration is a NUMBER here.
- I2V input fields: image_urls (array of image URLs; JPEG/PNG/WEBP, up to 10MB each; schema allows several but only the FIRST is used for the motion reference - 'More than 1 image provided; only the first will be used'); OR task_id (string, max 100 chars, references a prior grok text-to-image task; do NOT send image_urls and task_id together); index (0-5, default 0 - picks which of the 6 images Grok generated per task); prompt (English-only, max 5000 chars); mode ('fun'|'normal'|'spicy', default 'normal' - 'spicy' is NOT allowed with external/uploaded images); duration ('6'-'30' seconds, 1s increments); resolution ('480p'|'720p', default '480p'); aspect_ratio ('2:3'|'3:2'|'1:1'|'16:9'|'9:16', default '16:9', follows image size if omitted); nsfw_checker (boolean, default false).
- @image reference token: literal form is '@image' + 1-based index + a trailing space, e.g. '@image1 a sunset over the ocean'. Multi-tag chaining ('@image1 ... @image2 ...') is for the image-to-image / multi-image endpoints; the I2V endpoint is effectively single-reference.
- Async flow: createTask returns HTTP 200 with a taskId. Get the result two ways: (1) supply 'callBackUrl' and receive a webhook on completion (recommended for production), or (2) poll the Get Task Details endpoint with the taskId. Browse tasks/logs at https://kie.ai/logs .
- Clip length: native 6-30s per generation, 1s increments. For short-form, generate short 6s takes per shot and stitch (matches our content-engine grok pipeline) rather than one long generation; vary 'duration' per shot to vary cut length.
- Platform: kie.ai advertises Grok Imagine 1.5 (faster generation, improved motion physics, stronger visual consistency). Pricing/playground at https://kie.ai/grok-imagine and https://kie.ai/pricing - confirm current per-second video cost before any paid run.
